# Guide

This is what you need to get started: how to install the program, how to connect to a router, what to switch on at the router itself, and what to do when it does not work. There are no descriptions of individual windows. The program reads menus and fields from the router, and the meaning of the settings is explained by the makers; for MikroTik that is the RouterOS documentation. The project as a whole is described in [README.md](README.md).

**Русский:** [GUIDE.ru.md](GUIDE.ru.md)

## Installing

### Windows

Run the installer (`windows-setup.exe`) or the portable file (`windows-portable.exe`, no install needed). If the file has no publisher signature, Windows shows "Windows protected your PC": press "More info", then "Run anyway".

On its first start the portable file unpacks itself into `%LOCALAPPDATA%\NetworkHelm\portable\<version>` (about 200 MB) and keeps its settings in the `NetworkHelm data` folder beside it. If the installer or the portable file says the program does not support this version of Windows, you have Windows 7, 8 or 8.1. There are files marked `legacy` for them.

### macOS

Open the DMG and drag NetworkHelm into Applications. If the program is not signed by Apple, macOS refuses to open it the first time. Open System Settings, Privacy & Security, find the message about NetworkHelm and press "Open Anyway". When macOS asks about access to the local network, allow it: without it the program cannot reach the routers of your network.

### Linux

DEB and RPM go in through the package manager:

```bash
sudo apt install ./NetworkHelm-<version>-linux-amd64.deb
sudo dnf install ./NetworkHelm-<version>-linux-x86_64.rpm
```

The AppImage is not installed: make the file executable (`chmod +x`) and run it. It mounts itself through FUSE and needs `fusermount` from the `fuse3` or `fuse` package; without FUSE, start it with `--appimage-extract-and-run`.

### Android

Download the APK and open it; Android asks for permission to install from that source. On the first connection allow "Nearby devices" for the program. Without it Android keeps the program out of the local network, and instead of a login you see "Android does not let NetworkHelm reach the local network".

### iOS

There is no ready app, only an Xcode project. On a Mac with Xcode run `tools/ios/build-ssh.sh` once, then open `app/iosApp` and build the app for your own device.

The neighbour list, MAC-Telnet and Wake-on-LAN go by broadcasts, which iOS lets an app send and receive only with the multicast entitlement that Apple grants on request. Until the app has it, the Neighbors tab, the login by MAC address and Wake-on-LAN are hidden on iOS. With the entitlement, MAC-Telnet also needs the MAC address of the device, and the connection window asks for it: iOS does not tell it to apps, and the router answers to the address the client names. It is the Wi-Fi Address under Settings → Wi-Fi → (i) next to the network, and with a private address it differs from network to network. The ARP table is closed to apps, so the LAN scanner lists no MAC address and vendor there. The language of the app is set in Settings → NetworkHelm → Language.

## First connection

The connection window opens on start. Its fields:

| Field | What to enter |
| --- | --- |
| Address | the name or IP address of the router; add a port after a colon if it is not the standard one |
| Platform | the type of device; the program recognizes it by itself, and then "recognized" stands beside it |
| Protocol | the way to connect; grey entries are ports that gave no answer |
| Port | change it only if the service on the router listens on a non-standard port |
| User, Password | the account on the router |
| Remember the password | keeps the password in the protected storage of the system |
| Group, Comment | for order in the list of saved routers |
| Via router | connect through the SSH of another saved router, when the one you need cannot be reached directly |

As soon as you type an address, the program checks almost at once which ports of the router answer. It only tries to open a connection and reads the greeting, without logging in; from the answers it recognizes the device and picks a protocol. You can change the choice by hand. A router that guards against password guessing may count such a check as a login attempt and block your address. Then turn the check off in "Settings": the item "Recognize the device and check which protocols answer while the address is typed".

Press "Connect". The "Save" button puts the router in the list on the "Saved" tab, so next time you only pick it there: a click fills the form, a double click connects. The group of each router has a column of its own, and "In groups" beside "Import" puts the routers under a header per group, the ones without a group last; a click on a header folds or unfolds it, and the program keeps both for the next start. The "Neighbors" tab shows the MikroTik routers that announce themselves on your network. They do it every 30 to 60 seconds, and "Refresh" asks them to answer now. On a window 960 dp wide or more the form and the lists stand side by side at the full height of the window; the button at the right of the tabs moves the lists under the form and back. Under the form a bar divides the height between the two: drag it to give one more room, double-click it to give the form its own height back.

If the connection goes over a protocol without encryption (the API on port 8728, HTTP, SNMP v2c), a warning appears under the fields and the main window carries a "Not encrypted" mark. The password and all data then cross the network in the clear, so work like that only on a network you trust.

To open a configuration without a router, press "Open config file" or drop the file onto the connection window: an `/export` of RouterOS, an OpenWrt backup, a UCI file or a running-config of Keenetic (the output of `show running-config` or the startup-config file saved from the web interface) will do.

## Preparing the router

The program reaches a router through services it already has. If the service it needs is off or closed by the firewall, the connection fails and the program says which port gave no answer.

### MikroTik RouterOS

The services are visible in WinBox and in the console: `/ip service print`. Any of these will do:

| Way | Port | Notes |
| --- | --- | --- |
| TCP 8291 (WinBox port) | 8291 | the whole interface works over this one port, so no API, REST or SSH is needed; the program picks it first when the port answers; the login on this port does not work on RouterOS 6.42, pick the API there |
| API-SSL | 8729 | encrypted; needs a certificate: without one RouterOS answers with anonymous TLS, which the program does not use |
| API | 8728 | not encrypted |
| REST over HTTPS and HTTP | 443 and 80 | RouterOS 7.1 and later only, the `www-ssl` and `www` services |
| MAC-Telnet | UDP 20561 | for a router without an IP address; needs its MAC address and a shared layer 2 network, on iOS also the MAC address of the device |

A new MikroTik usually has the login `admin`, with an empty password or one printed on the sticker. If the user group lacks the rights for a menu section, the program marks the section and says which right is missing.

When the password of the user has expired (RouterOS asks for a new one after `/user/expire-password`), the program offers to set it right after the login. "Skip" goes on with the old one, and the router asks again at the next login. The question comes through the console of the router, so it is seen over TCP 8291, SSH and MAC-Telnet, not over the API.

To move to encryption, first connect another way. If the first attempt gives an error about TLS (API-SSL is on and has no certificate), pick "API (8728)" in the "Protocol" list. When the connection opens, click the "Not encrypted" mark in the main window: the "Prepare router" window opens. It has four steps, each of which you can tick or untick, and the commands run when you press Apply:

- issue a self-signed certificate and turn on API-SSL (8729);
- allow the API through an SSH tunnel (`forwarding-enabled=local`);
- add the user group `networkhelm` with the rights the program needs; a separate user for the program can go in it instead of `admin`;
- turn off the plain API (8728) and Telnet; while this connection goes over API 8728 the step is unavailable, since it would cut the connection.

After that connect over API-SSL; the program asks about the fingerprint of the certificate once.

### OpenWrt

Pick the OpenWrt platform. There are two ways:

- SSH, port 22. It needs the root password or a key. On a freshly flashed router you set the password in LuCI, under System, Administration.
- ubus over HTTP (port 80) or HTTPS (port 443). It needs LuCI with the ubus module of the web server and rpcd; you log in as root with its password. Such a login gets what the ACL of LuCI allows. The windows of DHCP leases, ARP and wireless clients answer "Permission denied", the forms show the options without the types and hints that LuCI gives them, and the parts whose config no installed application of LuCI names are left out of the menu. The ACL file of the [OpenWrt package](server/README.md#directly-on-an-openwrt-router) lifts all of that, and so does a login over SSH.

At the top of the main window you can switch the menu view: "OpenWrt view", "Unified view" (the menus the program has for any router) and "LuCI view".

### OPNsense

Create an API key on the router: System, Access, Users, the user you need, API keys. A file with the key and the secret downloads. In the program enter the key in "User" and the secret in "Password". The port is 443.

### pfSense

The package pfSense-pkg-RESTAPI version 2 has to be installed: without it pfSense does not answer the API. There are two ways to log in: leave "User" empty and enter a key from System, REST API, Keys as the password, or give the login and password of a local user.

### VyOS 1.4 and later

Turn on the HTTP API and create a key: `set service https api keys id <name> key <key>`, then `commit` and `save`. In the program the key goes into "Password"; VyOS has no user field. Every edit is applied and saved at once.

### Keenetic and Netcraze

Netcraze is the brand Keenetic sells its routers under in Russia; both run the same KeeneticOS, and the program treats them alike. It talks to the router over RCI, the HTTP interface the router's own web interface uses. Enter the login and password of the web interface, or leave the login empty and put an access token of KeeneticOS 5.2 (the section "Users and access") in the password. A user with the `readonly` tag gets the windows read only.

From the home network the address of the router and HTTP (port 80) will do. From the internet the router takes HTTPS only and answers HTTP with "403 insufficient security level". Connect to its cloud name on port 443: KeenDNS gives names in keenetic.link, keenetic.pro, keenetic.name and keenetic.io, CrazeDNS of Netcraze in netcraze.link, netcraze.pro, netcraze.club, netcraze.io and crazedns.ru. Typed into the connection window, such a name picks Keenetic over HTTPS at once, without probing the ports of the cloud. Where HTTPS is forwarded to another port, the address still has to be the name and not the IP: without the name in TLS the router breaks off the handshake. The cloud answers one name from several nodes, and a node may show a certificate of its own instead of the router's: the program then shows the window with the fingerprint and Trust again rather than dropping the connection.

The menu, the windows and their fields take their names from the dictionary of the router's own web interface (`/assets/language/locale.<language>.json`), in the language of the program: with the program in Russian the menu reads Системный монитор, Интернет, Мои сети и Wi-Fi, Сетевые правила, Управление, as in the web interface of that router. A field the web interface does not show, such as the counters of errors of an interface, keeps the program's own name. A router without the dictionary of the language gets the English names.

The System Dashboard has the cards of the web interface. Internet: the connection with a graph of its rates each second, its address, mask, gateway, MAC address, DNS servers, KeenDNS name, content filter and traffic. About the System: CPU and memory, model, KeeneticOS, update channel and auto-update, uptime, time, active connections, access from the internet, the mode of KeenDNS, the service tag and the serial number. Applications: the WireGuard and OpenConnect servers, on or off. My Networks: the home networks with their clients on Wi-Fi and on the wire and their access points with band, channel and protection. Network Ports: the speed of each port and the one that goes to the internet. Wi-Fi Monitor: the load of the channel of each radio, its width, clients and temperature, and the extenders of the Wi-Fi system. Traffic Monitor: the hosts that sent and took the most in the last three minutes. All of it is one request to the router, as the web interface asks it; a router with a weak processor is not kept busy. Whether an update is available the dashboard does not say: the web interface asks the update server for it (`components list`), the program does not.

The menu follows the web interface: the same five groups, the same entries in the same order and with the same names. An entry shows when the web interface would show its page to this router: the program reads the installed components (`show version`) and the mode (`show system mode`) and checks the same conditions the code of the web interface does. Without the corewireless component there are no access points, Wireless ISP, Wi-Fi Monitor and Wireless ACL, without mws no Wi-Fi System, without the components of USB modems no Mobile, without QMI and LTE modems no SMS and USSD, without dsl and usbdsl no DSL, without ntce no IntelliQoS, without storage no Storages and Devices, without opkg no OPKG, without wireguard, openvpn, ipip, gre and eoip none of their tabs in Other Connections, without ndns and ddns no Domain Name, and a router in extender mode has no internet pages and no network rules. Status: the System Dashboard, the Traffic Monitor (the ten clients that received and sent the most in the last three minutes, with their rates) and the Wi-Fi Monitor (each radio with its channel, width, channel load and clients). Internet: Ethernet Cable (the cable connections and PPPoE over them), Mobile (USB modems), DSL (the state of the line and its settings), Wireless ISP (a connection to someone else's Wi-Fi network), all with live rates, traffic and the internet check; Other Connections with tabs for the VPN connections (PPTP, L2TP, SSTP and the other kinds), WireGuard and its peers, OpenVPN, the IPIP, GRE and EoIP tunnels and IPv6 over IPv4; Connection Policies; SMS and USSD of the modem. My Networks and Wi-Fi: clients, access points, segments, the Wi-Fi System with its extenders and settings, IntelliQoS. Network Rules: Internet Safety (content filter, DNS configuration, DNS interception, DNS proxy), the firewall with IPv4 and IPv6 tabs, port forwarding with the UPnP rules, routing, the KeenDNS domain name, Wireless ACL. Management: the system with firmware, time synchronisation, configuration, LEDs and buttons; Storages and Devices (USB drives with their partitions); Applications, the list of applications of the web interface (VPN servers, SMB, media server, UDP proxy and others) with whether their component is installed, and the tabs of the OpenConnect and WireGuard servers; users and the services they may use; Diagnostics with Ping, Traceroute and active connections; OPKG. Windows the web interface has no page of their own for stand at the end of their groups: DHCP Server and ARP under My Networks, DNS and NAT under Network Rules, clock, resources and schedules under Management. At the bottom of the menu: Interfaces (every interface of the router with live rates), IPv6, the system log (the last 500 lines, then only the new ones) and the command line.

All Settings is made from the router itself. The program asks the CLI of the router what commands it has (`help`, as the web CLI does for its hints) and makes a window of each context that keeps settings, such as ip http, ip ssh, dns-proxy, system clock or ntp, and of each interface with every setting its kind has: MTU, MAC, address, IPv6, ping check, schedule, rate limit, the authentication of PPPoE. In the menu an interface goes by its name alone, Bridge0 or WifiMaster0/AccessPoint1; its window is titled with the whole context, interface Bridge0. A command that keeps one value is a text field, one with choices a list, one with several values a field for each, one that is on or off a check box; the help of the command is the hint of the field. Commands that do something rather than keep a value, such as reboot or the generation of keys, have no field. A newer KeeneticOS or another model gets its own settings without a new version of the program. In the menu these windows are grouped by the first word of the context: Interfaces, IP, IPv6, DNS, Mesh Wi-Fi System, System Settings, VPN and Other; a context with nothing to set, such as `cloud` or `eula`, has no window. The router describes its commands the same way for one firmware, so the program keeps the descriptions and the dictionary on the disk under the model, the release and the components: the first connection reads them (about 10 seconds through the cloud), the next ones take them from the disk.

What can be changed besides: a client's name, internet access and permanent IP address (naming a client registers it, removing it forgets it); the SSID, password, security (none, WPA2-PSK, WPA2-PSK + WPA3-PSK, WPA3-PSK) and on/off of an access point; the name and description of segments, connections and interfaces; firewall rules, each in the access list of its interface and direction as the web interface keeps them, moved by dragging, switched off and described; static routes, NAT, DHCP pools and static leases, own DNS servers, users with the services they may use, the router's host and domain name; new PPTP, L2TP and SSTP connections with server, user and password, the description and on/off of a connection of any kind (RCI takes no server for the other kinds, they are made in the web interface); connection policies with description and multipath; the access list of each access point (off, white list or black list) with the MAC addresses of registered clients (the router refuses others: "MAC address … is unknown"). The protocol of a firewall rule is TCP, UDP, ICMP, ESP, GRE, IPv4, IPIP, the number of another protocol or a service from the list of the web interface, such as "TCP/22 - Secure Shell (SSH)": a service goes to the router as its protocol and destination port. KeeneticOS keeps no ICMP type and code in IPv4 access lists. The addresses of a rule are written as 192.0.2.0/24 or a single address, an empty field means any; ports as 22, 1000-2000, <1024 or >1023. A port forwarding rule is made as in the web interface: input (an interface or a subnet), output (this router, a registered client, another address or an interface), a protocol from the list of the web interface (TCP, UDP, TCP/UDP, ICMP, all protocols and 41 services), a single port forwarded to another one or a range, and a schedule; rules are moved by dragging and switched off with a toggle. The connections to the provider are edited as in the web interface: the IPv4 setting (automatic, manual or not used) and IPv6, DNS servers and ignoring those of the provider, the MAC address, the device name, MTU, 802.1x, Ping Check, a PPPoE, PPTP or L2TP tunnel over the cable with its account, and the priority of the connection; Wireless ISP adds the network, security and key, BSSID, always on or on demand, and TTL; a modem adds the APN, the network type and roaming. A WireGuard connection is made of the text of a .conf file (the router reads it itself, as Load from File of the web interface does) or of the fields with a key pair the router makes. The router never gives the private key back: an empty field leaves it as it is, and a separate button makes a new pair. Peers are a list of their own with the address and port, allowed subnets, keepalive and the preshared key. OpenVPN is made of the text of an .ovpn file, an IP tunnel with its address, far end and source, IPv6 over IPv4 with the address of the broker. IPv6 firewall rules work as the IPv4 ones and keep the ICMPv6 type and code. A schedule is a line such as start 08:00 mon,tue; stop 17:00 mon,tue, `*` for every day. The LEDs: a mode (all on, all off, the main ones or the port LEDs off) with a schedule, and the job of each LED; the buttons: what a press, a double press and a long press do (a job the router protects, such as the reset at a long press of Reset, is only shown). Firmware: the channel and automatic updates; Check for Updates asks the update server, and Update KeeneticOS, after a confirmation, downloads the version, writes it to flash and restarts the router. SMS messages are sent, marked as read and removed; a USSD request waits up to a minute for the operator; a USB drive is ejected safely. DSL, OPKG and IntelliQoS are shown only. The comparison of configurations works with Keenetic too: the running-config is split by the contexts of the CLI. A change applies at once, and in the same request the program asks the router to save its configuration, as the web interface does.

The password of a user goes to the router as the MD5 hash of user:realm:password and as the NT hash, the two hashes the web interface sends; the NT hash is what the VPN servers with MS-CHAP check.

The command line sends each line to RCI (`parse`), the way the web CLI of the router does, and prints the answer as the CLI prints it over SSH: the names of the fields aligned at the colon, an inner block to the right of it. The context stays from line to line (`interface Bridge0`, then `description …`, then `exit`). A long command such as `tools ping 8.8.8.8` prints its lines as the router gives them, and Ctrl+C stops it in the router too. The real CLI over SSH is open on the home network only (`ip ssh` keeps the security level private). Where SSH of the router is forwarded from the internet, put its address and port into the field "SSH" of the connection window, 192.0.2.1:2222 for example: the command line then goes over SSH with the login and password of the web interface. Telnet the program does not use.

A router can also be managed over SSH alone, with its web interface closed to the internet: the "RCI over SSH" method of the connect screen. Address and port are those of the router's SSH, user and password those of the web interface. Over SSH the program learns the address of the router's home network (`show interface`) and reaches RCI through an SSH tunnel to that address: the router does not answer with its web interface on its own loopback. The windows and the command line share the one SSH connection.

Checked on a Keenetic Launcher (KN-1221) with KeeneticOS 5.1.8 through CrazeDNS and through its SSH forwarded to port 2222: every window and the menu by the router's components; IPv4 and IPv6 firewall rules, port forwarding rules of every kind, a schedule and a WireGuard connection with a peer were made, changed and removed, and after the checks the router's configuration matches the original. The settings of the connections to the provider were only read there: they carry the tester's internet. The router has no modem, DSL or USB, so SMS, USSD, DSL and storages are not checked on a real router; the firmware install was not run.

### Linux over SSH

Pick "Linux / SSH host" in the list of devices. On a Linux host the program reads interfaces, addresses, routes, neighbours, sockets (`ss`), storage, processes, services and the log (journald or logread), and changes what an administrator changes over SSH. Commands that need root run as they are when the login is root, through `sudo -n` when sudo lets the login in without a password, and through `sudo -S` with the password of the login otherwise. With a key, type the password into the password field as well: it goes to sudo only. Each command through sudo is a line in the log of the host, so the windows that need root are read every 30 seconds and at once after a change made in the program. Commands of the windows take six SSH channels at most: OpenSSH opens ten on one connection (MaxSessions), and the terminal and Files get the rest.

The host's dashboard: CPU load with a chart, memory and swap, load average, distribution, kernel, architecture, virtualisation, processor, uptime; the network, with the interface of the default route and its rates each second, the addresses of the interfaces, gateway and DNS; disks and how full they are; services: failed ones, how many run, how many ports listen, the firewall, whether a reboot is required; the processes that take the most CPU and memory; who is logged in; temperatures where the kernel gives them. Sockets: every connection, and a Listening Ports tab with port, address, protocol, process with its PID and user, as `lsof -i` or `ss -tulnp` show them. Process memory is in KB, MB and GB. The windows call such a machine a host, not a router.

Interfaces: MTU, comment and on/off; the Virtual tab makes and removes VLANs (on a chosen interface, with an id of 1-4094), bridges, dummy interfaces and tunnels to another host: GRE with an optional key, GRETAP, IPIP, SIT, VXLAN and GENEVE with a VNI and a UDP port (4789 and 6081 unless another is given; without a port the kernel would put VXLAN on 8472). A tunnel without a local address takes the one the host leaves by toward the remote end. Keep After Reboot keeps a tunnel in netplan, NetworkManager, systemd-networkd or ifupdown, except GENEVE, which netplan and NetworkManager do not know. The tunnels the kernel makes for itself as a module loads, gre0, tunl0, sit0 and the like, are not shown. Addresses and routes are edited in place, added and removed, static neighbours added and removed, all with `ip`, that is in the running system. The Keep After Reboot box of a form writes the same change to the network configuration of the distribution, so it survives a reboot: to the NetworkManager profile (`nmcli connection modify`), to a netplan file of its own, `/etc/netplan/90-networkhelm.yaml`, checked with `netplan generate`, to a `networkhelm.conf` drop-in of the systemd-networkd `.network` file, or as `post-up`/`pre-down` lines in the ifupdown stanza of the interface, checked with `ifquery`. Nothing is restarted: the running system has the change already. A file is copied before it is written, and the copy comes back if the check fails. Removing an address, a route or a virtual interface removes it from the configuration too, where it is written there. wicked, the old ifupdown form with `address` and `netmask` and one-line netplan files are not edited; where there is no manager, the box answers that the change lasts until a reboot. The program does not switch off or remove the interface the session came through, nor remove the address it came to.

Storage: mounted file systems and how full they are, with mount, remount and unmount; disks and partitions (`lsblk`) with model, serial number and file system; the entries of `/etc/fstab`; SMART (`smartctl`): health, temperature, power-on hours, reallocated and pending sectors, wear, and a short test of the chosen disk. A container has no SMART, it has no disks.

The log of the host has tabs: System, the whole log; Kernel, the messages of the kernel; Authentication, logins and sudo (facilities auth and authpriv); Errors, messages of level err and above; Previous Boot, the log of the boot before, where journald keeps it on disk. Where there is journald the program reads it (`journalctl`, then only the lines after the last one read); without it, the buffer of `logread`, the files `/var/log/messages`, `/var/log/syslog`, `/var/log/auth.log`, `/var/log/secure` and `dmesg`. A login outside the groups `adm` and `systemd-journal` on Debian and Ubuntu sees only its own lines of the journal, so the program reads such a log as root. Each read through sudo is itself a line of the log, so those tabs are read every 30 seconds; a root login reads them at every poll. An LXC container gets no messages of the kernel: its Kernel tab stays empty.

Firewall shows what manages the host and a tab for each tool it has. ufw: the rules, numbered as `ufw delete` numbers them whether ufw is on or off, added with action, direction, protocol, ports, addresses, interface and comment; the settings: on or off, the default policies, logging. ufw is not turned on without a rule for the port of the session: it keeps the running session and refuses the next login. firewalld: the services, ports, protocols, sources, interfaces and rich rules of each zone, added to and removed from the running and the permanent configuration at once; the zones with their target and masquerade, Make Default, Reload and Keep Runtime as Permanent. nftables: the rules with their handles and counters, added to a chain of a table and removed by handle; the chains with hook, priority and policy. iptables and ip6tables: the rules of each table and chain in the order the kernel checks them, added at the end or at a position; the chains with their policies and counters. Save for Boot writes the rules where the service of the distribution loads them: /etc/iptables/rules.v4 on Debian and Ubuntu (loaded by iptables-persistent), /etc/sysconfig/iptables on Fedora, RHEL and openSUSE, /etc/iptables/rules-save on Alpine, /etc/iptables/iptables.rules on Arch, and /etc/nftables.conf, /etc/sysconfig/nftables.conf or /etc/nftables.nft for nftables. Where ufw or firewalld keeps the rules, they write them again when they start, and the program does not save over them.

Before each change of the firewall the host keeps the rules it has (iptables-save, nft list ruleset, a copy of /etc/ufw or /etc/firewalld) and starts a job that puts them back in 60 seconds. After the change the program runs a command over the same connection; when the host answers within 10 seconds, the job is removed. A change that cuts the session thus undoes itself within a minute. A rule that keeps the running session and refuses new logins is caught by a second login: before the first change of the firewall the program logs in to the host once more with the same address and credentials and, when that login gets in, repeats it after every change. When it no longer gets in, the rules it had come back at once and the window says why the change did not stay. A host that refuses the user a second session is checked through its session alone. Each such login is a line in the log of logins of the host.

Rules of ufw, nftables and iptables are edited in place and moved by dragging their rows, firewalld rules are edited in place. When a firewall change fails, the rules saved before it come back at once, without waiting the minute.

Packages through the manager the host has (apt, dnf, yum, zypper, pacman, apk): Installed, where New installs by name and Remove removes; Updates, with Upgrade of the selected ones, Upgrade All and Refresh Lists. Each command answers with what the manager printed. Services of systemd and OpenRC: Start, Stop, Restart, Reload, Enable and Disable, and whether a service starts at boot in a column. Processes: Hang Up, Terminate and Kill.

The terminal of such a host has a button that makes the console root: it types `sudo -s` and gives sudo the password of the login when sudo asks for it.

Checked in LXC containers with Debian 12 (ifupdown), Ubuntu 24.04, Fedora 44, Arch Linux and openSUSE Leap 16 (systemd-networkd), Rocky Linux 9 (NetworkManager) and Alpine 3.24 (ifupdown-ng, OpenRC and busybox): on each a dummy interface and an address on it were made with Keep After Reboot and removed, and the configuration came back the same. SMART was checked on a Proxmox node with two SATA disks.

### VPN on a Linux host

Configurations and profiles for clients open as text to copy, with a QR code when the text fits into one.

Users shows for each user an Apple profile (`.mobileconfig` with the CA), an Android profile for the strongSwan app (`.sswan`) and a PowerShell script for Windows. PPTP gives the logins and the traffic of its users to anyone who records them, as MS-CHAPv2 and MPPE are broken, so its wizard makes a server only with Insecure, Create It ticked and a change of the server needs Insecure, Change It. OpenConnect is ocserv: its settings, a certificate for the name clients reach it by, whose pin the clients take, and the users of its ocpasswd file. A changed file goes through `ocserv --test-config` and comes back when that fails; a running server takes it with `occtl reload`, or restarts when its ports or network changed. OpenConnect Client and SSTP Client make a unit of systemd for each connection: openconnect reads its password from a file of mode 600, sstpc leaves it to pppd, which finds it in chap-secrets. An SSTP connection checks the certificate of the server against its CA file or the CA bundle of the system unless Skip Certificate Check is ticked; it can take all the traffic of the host, the way to the current session staying outside the tunnel, use the DNS of the server and set the MTU. AmneziaWG has the window of WireGuard for awg-quick in /etc/amnezia/amneziawg, with peers, client configurations with QR codes, New Server and Import Client Config, and a Disguise tab: Jc, Jmin, Jmax, S1, S2 and H1–H4, and S3, S4 and I1–I5 where the awg of the host lists them (versions 1.5 and 2.0). On a host of OpenRC, such as Alpine, Start at Boot first puts in /etc/init.d/awg-quick, a service no package brings. Tailscale shows the node, its settings and the peers of its tailnet. A network shows its routes and DNS servers, the Peers tab lists the roots and nodes with their latency and path, and the Node tab sets the port, port mapping and the TCP relay in local.conf, after which the service restarts under the guard.

Users is one list over all servers, as PPP Secrets in RouterOS: a peer of WireGuard by the name in its comment, a certificate of OpenVPN by its common name, a secret of EAP, a user of ocpasswd and a line of chap-secrets of L2TP or PPTP are one user where the names meet. A new user gets what each chosen server needs and one password for every service that takes one; when none is given, the host makes one only for a user of IKEv2, whose secret keeps it to be shown again. Turning a user off, taking a server from it and removing it act on every server it is on; a session of L2TP or PPTP lasts until its client leaves. Connections shows a tile for each service with its port, sessions and rates, a chart of the rates and the live sessions, read every 3 seconds: peers of WireGuard and AmneziaWG with a handshake under three minutes, clients of OpenVPN from its status file, IKE SAs of strongSwan, users of ocserv with the client program they report, and sessions of accel-ppp. The bytes of a WireGuard or AmneziaWG peer are counted since its interface came up, not since the session began. The Connection Log takes OpenVPN and charon from the journal of systemd. ### Proxy servers on a Linux host

Overview lists Squid, tinyproxy, 3proxy, Dante, shadowsocks-libev, sing-box and Xray with whether each is installed, the state of its service, the ports its process listens on and its config file; Install Now installs the chosen rows after a confirmation and shows what the installation printed: packages in one call of the manager of the host, and Xray and sing-box, where the repositories have none, from the latest release on GitHub, whose page the Packages column then shows. A release puts the program in /usr/local/bin, for Xray also geoip.dat and geosite.dat after checking the archive against its .dgst, a service of systemd or OpenRC and an empty config where there was none; curl and unzip come from the manager where the host lacks them. Squid: the ports, cache, DNS, timeout and log settings of squid.conf (sizes and times with their units, 256 MB or 30 seconds, as Squid reads a bare number as bytes or seconds), a parent proxy every request goes through (cache_peer with never_direct), caching on or off (cache deny all), the http_access rules in their order (a new rule goes before `http_access deny all`, and dragging keeps the rules on their sides of an `include`), the acl lines, and the users of basic_ncsa_auth, whose passwords are hashed on the host (`openssl passwd -apr1`, or `cryptpw` of busybox where openssl is missing). A changed squid.conf goes through `squid -k parse` and comes back when that fails; a running Squid takes it with `squid -k reconfigure`, and a new cache_dir restarts it. Basic Auth of Users adds the rule that lets the users in before `deny all`; the package of Debian, Fedora and Alpine allows `localhost` above it, so from the host itself Squid still goes without a login. tinyproxy: the port, the listening and outgoing addresses, the allowed and denied clients, the ports CONNECT may reach, limits, the Via and X-Tinyproxy headers, the upstream proxy and the users of BasicAuth, whose names and passwords take letters, digits, dots, dashes and underscores alone, as tinyproxy parses them; tinyproxy has no check of its file, so a running one is restarted, and when it does not come up within 3 seconds the old file comes back. Squid also sums up its access log of the last 30 days, rotated and compressed files as well, by clients and by sites: the requests and the bytes of the last day, week and month. shadowsocks-libev: the server of its config.json (addresses, port, password, an AEAD cipher, mode, timeout, plugin, TCP Fast Open, reuse of the port, no delay, IPv6 first and the DNS servers of ss-server), restarted with the old file back if it does not come up, and Client Link, the ss:// link of SIP002 with its QR code; a server on loopback or on every address gets the address the session reached the host by. The package of Debian runs the server with DynamicUser and needs config.json readable by all, so any user of the host can read its password. Dante (danted on Debian and Ubuntu, sockd on Fedora, Arch and Alpine): the settings outside the rules (internal, external and the rotation of its addresses, the SOCKS and client methods, the users it runs as, the timeouts of negotiation, connection and idle traffic, the log), the client and socks rules in the order Dante checks them (a new rule goes before the rule of its kind for any address), and the users of the method username, accounts of the system without a shell whose passwords go to chpasswd. A changed file goes through `danted -V` or `sockd -V` and comes back when it fails; the file the packages give has no internal address and fails it until one is set. The method username checks passwords against /etc/shadow, which only root reads, so with it the program sets `user.privileged: root` (Debian gives proxy there, and the logins fail with it); a new rule logs `error connect disconnect`, as without `log:` Dante writes nothing of the clients of a rule. 3proxy (packaged by Fedora): the settings before its rules (DNS servers and the size of their cache, log and its rotations, connections, timeouts, addresses), the lines of auth, allow, deny and flush together with the services they apply to, in the order of the file and moved by dragging, as 3proxy reads them in that order, and the users of its users lines, a new password stored as an MD5 crypt (CR); 3proxy has no check of its file, so a running one restarts, and the old file comes back when it does not come up. sing-box and Xray: their inbounds (tag, kind, address, port, TLS or Reality, transport, users) and users in tables, a new user with a UUID or password the host makes, Client Link for VLESS, VMess, Trojan, Shadowsocks and Hysteria2 with its QR code (for Reality the program makes the public key from the private one itself), and config.json whole in the editor of Edit config.json: `sing-box check -c` or `xray run -test -c` reads the new file in its place, and it comes back when the check fails or the service does not come up. New on the Inbounds tab (or New Server on the Service tab) is the wizard of a server of one of the schemes VLESS + REALITY, Shadowsocks 2022, Trojan + TLS, VLESS + WS + TLS and, with sing-box, Hysteria2 with the salamander obfuscation, the certificate signed by the program itself, files of the host or ACME of sing-box (links of a server with a self-signed certificate let a client of sing-box skip its check and a client of Xray pin it, pcs): the tag, the port (443, then 8443, then a free one above 20000), the site Reality borrows its handshake from (dl.google.com) and the name of the first user come filled in, the kernel makes the UUID, the program itself the key of Reality and /dev/urandom the short ID; the file goes through the check, the service starts and starts at boot, and when it does not come up the old file comes back and the service stops. The wizard removes the shadowsocks inbound of the example config of the package of sing-box, whose password is in the repository of sing-box. Client Links of an inbound gives the links of all its users with their QR codes, and Remove removes the inbound. The form of an inbound changes all its settings: the tag, the port and the listening address, the transport (network, path, Host, the service name of gRPC), TLS or Reality (server names, ALPN, the files of the certificate, the target, the short IDs and the private key of Reality), sniffing of Xray, the cipher and key of Shadowsocks and, with sing-box, salamander and the speeds of Hysteria2. A secret left empty after + is made anew by the host; an inbound turned to Reality gets a key, a short ID and the site of the wizard, one turned to TLS without a certificate one the program signs itself, and a new tag or port moves the rule of ufw or firewalld. A user can be renamed and given another flow or a new secret. The Outbounds tab lists the outbounds with their server, the outbound they dial through and which one is the default; New makes a direct one, a block one (Xray) or one to the server of a link, which can dial through another outbound for a chain, and Make Default puts an outbound first (and removes route.final of sing-box). An outbound a rule, a chain or the default still names is not removed. The Routing tab keeps the rules in their order, moved by dragging: domains (with subdomains, or full:, keyword:, regexp:), geosite, geoip, addresses and inbounds go to an outbound or to block, the blackhole outbound of Xray and the reject action of sing-box. Geosite and geoip are the files of Xray and, for sing-box, which has no geosite of its own since 1.12, the rule sets of SagerNet that sing-box downloads when it starts. Block Ads adds the rule that blocks category-ads-all. Conditions the form does not take, such as ports, stay in the rule and show under Other Conditions. The links come up at once after OK of the wizard. The wizard opens the port of the new server in ufw or firewalld where one keeps the rules, and Remove of the inbound closes it. Install Now removes the shadowsocks inbound of the example config of the package of sing-box, whose password is published in the repository of sing-box, right after the installation; while it is in the file, the service of sing-box neither starts nor starts at boot and the file is not saved. The Clients tab of Xray and sing-box makes a client on this host from the link of a server (vless://, vmess://, trojan://, ss://, hy2://; Xray without Hysteria 2): a file of its own, /etc/networkhelm/<program>/<name>.json, and a service of its own, <program>-client-<name>, so a server of the same program on the host keeps its config. The client takes SOCKS on 127.0.0.1 (sing-box HTTP on the same port as well); its file goes through the check of the program, and its service starts and starts at boot. The client of sing-box up to 1.14.4 does not reach a server of REALITY on Xray 26, as it sends no X25519MLKEM768, so for a link of REALITY of a server of Xray the Clients tab of sing-box of these versions refuses and offers the client of Xray. A file with the comments Xray allows is no JSON for the tables and is changed in the editor alone. Xray 26 from its release was checked on Debian 12 and Ubuntu 24.04: servers of VLESS with REALITY and of Trojan with TLS made by the wizard carried requests of the clients of Xray made from their links. System Proxy writes one address with its login to `/etc/environment` (which pacman and apk read too), to a file of apt of its own, to `dnf.conf`, to `/etc/sysconfig/proxy` of zypper and to a drop-in of the unit of Docker, which restarts Docker. Passwords stand in those files as the programs need them; the windows never show them back, and an empty password field keeps the old one.

### Containers on a Linux host

When the host has `docker` or `podman`, the menu gets a Containers group, one window with a tab for each of its entries. The windows of what Install Now or the Packages window puts on the host show in the menu at once, and those of what they take off leave it, without connecting again. The program speaks to the API of the engine through `docker system dial-stdio` (`podman system dial-stdio`) in a channel of the SSH session, as `docker -H ssh://` does: nothing is installed on the host and no port is opened. The engine is reached as the login when the login may use it: root, a member of the group `docker` (that group is as good as root on the host), rootless Docker through `DOCKER_HOST` or the socket in `$XDG_RUNTIME_DIR`. When the engine answers "permission denied", the program goes through sudo, as the other windows of the host do. A login other than root goes to the system Podman through sudo when `/run/podman/podman.sock` exists, and to its own Podman otherwise; when the socket of the login does not answer, the program starts `podman system service --time=900`, which ends by itself after 15 minutes without connections. A `docker` command that is the script of podman-docker counts as Podman. Podman 3 (Ubuntu 22.04) has no `dial-stdio`, and the program does not reach it. The group always has Overview: Docker, Podman and Compose with their versions and the packages the distribution names them by (docker.io on Debian and Ubuntu, moby-engine on Fedora, docker-ce and docker-compose-plugin from the repository of Docker on RHEL and its kin, docker-cli-compose on Alpine, podman-compose where Podman stands alone). Where `docker` is the script of podman-docker, the Docker row says so and offers no package: moby-engine conflicts with podman-docker. Install Now puts in the rows chosen with the package manager of the host once asked and shows what it printed; Docker that was not there starts at once and with the host (`systemctl enable --now docker`, on Alpine `rc-update` and `rc-service`). Where Compose v1 alone stands (`docker-compose` 1.29.2 of Ubuntu and Debian 12), the row of Compose offers v2, and v1 has a row of its own with no package. On a host without an engine Overview is all the group has. The entries of the group open one window, Containers, with a tab each in the order of the menu (Overview, Containers, Images, Volumes, Networks, Stacks, Pods with Podman, Registries, Monitor, System); on a host without an engine it has Overview alone, and the tabs of the engine come within five seconds of an installed engine answering. A login in the group `docker` is root on the host through Docker, and on the first connection that finds it the program says so in a line above the windows, once for each host.

Containers: a row starts with the letters of its state, as the flags of RouterOS: R running, P paused, S restarting, X stopped, E stopped with an error code or dead, H healthy, U unhealthy; then name, stack (the Compose project), image, status, creation time, address, published ports, CPU and memory, and the column menu adds the rest; Start, Stop, Restart, Pause, Resume, Kill, Hang Up, Recreate with Pulled Image, Duplicate, Save as Image and Remove with Volumes. The form of a container has the tabs of `docker run`: General, Env, Ports, Mounts, Network, Resources, Restart, Healthcheck, Security, Logging and Runtime, and its values are written as on the command line (`8080:80/tcp`, `src:dst:ro`, `512m`, `1m30s`). CPU, memory, pids and the restart policy change in place (`docker update`), a new name renames the container; any other change recreates it, and only with the Recreate box ticked. The old container is renamed, the new one is made and started, and only then the old one is removed; when a step fails, the new one goes and the old one gets its name back and starts again. Variables whose names hold pass, secret, token, key, credential, private or auth stand in the field Secret Variables: their values are not read back, an empty value keeps the old one, and Inspect shows them masked. With "Hide passwords and keys" on, every line of the field stands as dots with an eye, as a password does, and the journal shows its values as dots. The window of a container has the tabs Logs (follows the container; a filter, the last 100, 500 or 5000 lines or all, time stamps, Save writes the shown lines to a file; stderr in another colour), Terminal (`exec` with a shell and a user, or `attach`), Stats (CPU in percent of one core, memory against its limit, network and disk per second, for the last two minutes), Processes (`top`), Inspect, Changes (`diff`) and Files (a list that `ls -la` reads inside the container, empty for an image without ls, such as distroless or scratch; downloading and uploading through the archives of the API).

Images: a row for each tag with its ID, size, creation time and how many containers use it; Pull with the progress of each layer, Pull Again, Tag and Push, History, Inspect, Remove and Remove Forced, Save to File and Load from File (the file stays on the host, Files brings it to the computer). Volumes: driver, mount point, how many containers mount it, whether it is anonymous; a new volume takes a driver, options and labels. Browse shows the files of a volume through a helper container: `alpine:latest` with the volume in `/volume` and no network, made only after you agree and removed when the window closes, at the latest after an hour. Networks: bridge, macvlan and ipvlan with subnet, gateway, range, IPv6, parent interface and mode, internal and attachable; the containers of a network, connecting a container with an alias and an address, disconnecting it. Docker takes no aliases on its default bridge, and the window says so before asking it. Prune of containers, images, volumes and networks first lists what would go and removes the ticked ones one by one, so an element the engine keeps does not stop the others.

Stacks are the Compose projects found by the labels of their containers and the folders `~/stacks/<name>` that hold a Compose file. The program runs `docker compose` or `podman compose`, otherwise `docker-compose` or `podman-compose`, in the folder of the stack and the way the engine is reached (through sudo, as root): Up, Down, Down with Volumes, Restart, Pull, Build, the services with their state, one log of all containers of the stack, and editing compose.yaml and .env, where Compose reads the stack with the draft (`config`) before the file is replaced. A new stack is written into `~/stacks/<name>` from the window, from a template or as a clone of a Git repository; Compose reads it before it starts, and a stack it cannot read does not stay. Ten templates come with the program: nginx, PostgreSQL, Redis, Home Assistant, AdGuard Home, Uptime Kuma, WordPress with MariaDB, Gitea, Grafana and Prometheus, with placeholder passwords in their .env; Save as Template in the editor of a stack adds your own. Registries keeps the logins of registries where the program keeps passwords (see Where the data lives). A login goes in the `X-Registry-Auth` header with each pull and push of its registry from the windows Pull and Tag and Push, with the pull of Recreate with Pulled Image, and with the one a new container or a recreate from the form needs when the host lacks the image; it stays nowhere on the host. Compose pulls the images of a stack with the logins of the host alone; `docker login` on the host runs only at the button Log In on the Host, with the password on stdin.

Monitor has the tabs Engine (version of the engine and its API, operating system, kernel, storage driver, cgroup, processors and memory, containers by state, images, root folder, whether the engine is rootless, and the state of Swarm, which the program only shows; below them, the containers that take the most CPU and memory), Events (what the engine kept of the last hour or 24 hours, then what happens, with a filter by kind and by name, image or ID), Disk (`system df`: how much images, containers, volumes and the build cache take and how much of it a prune would free); System has daemon.json and Prune of containers, images, volumes and networks; the build cache is not pruned here. Pods of Podman: status, containers, how many of them run, networks; Start, Stop, Restart, Pause, Resume, Kill, and removal together with the containers.

A macvlan or ipvlan network whose parent is the interface the session came through (or a VLAN on it), a container connected to such a network from the window of the network and a saved daemon.json go through the same guard as a change of the firewall: the host puts the old state back in 60 seconds unless the program reaches it after the change, and the second login checks that new sessions still get in. daemon.json is first checked with `dockerd --validate --config-file`; then it is written, Docker restarts (`systemctl restart docker`, `rc-service docker restart` on Alpine), and the program waits up to 30 seconds for `docker info`. When a step fails or the session is lost, the old file comes back and Docker restarts again. A container that the form makes, Duplicate copies or Recreate makes anew on such a network goes without the guard. A rootless engine reaches no interface of the host and needs no guard. Podman has no daemon.json, and rootless Docker keeps its own in `~/.config/docker` of the login and restarts with `systemctl --user restart docker`; the tab changes the file of the system Docker alone and says so for both.

Checked in LXC containers with Arch Linux (Docker 29.9.3, Compose 5.7.1) and Fedora 44 (Podman 5.8.9, podman-compose 1.6.0): containers were made from the form, changed, recreated and removed, a stack of two services went up, was edited and went down, pods, a volume browsed through the helper container, networks with aliases, and daemon.json saved under the guard (12.8 seconds with the restart of Docker). Push to a registry, a pull from a private registry with a saved login, rootless Docker, the Podman of a login other than root and macvlan on the interface of the session were not checked on a real host.

### Other devices

Pick "Other device". SSH is enough for Linux. UPnP and TR-064 find the device on port 1900 (a FRITZ!Box serves its description on port 49000) and are read only.

SNMP v2c reads interfaces, addresses, routes, ARP, neighbours and storage into windows of their own; the community goes in the field "Community", which shows what you type and starts as `public`; there is no user field. SNMP v3 needs a user name and passwords.

After the main menu appears, the program walks the agent the way `snmpwalk` does: the trees mib-2 (1.3.6.1.2.1), enterprises (1.3.6.1.4.1) and the SNMP modules (1.3.6.1.6.3). The walk takes at most 12 seconds and 20 000 objects, reads 20 rows of each column and 500 objects of each subtree it does not know; the windows read the rest when they open. While it runs, the windows of the main menu already work; when it ends, a "MIB" group appears in the menu with one window per MIB module (IF-MIB, Q-BRIDGE-MIB, POWER-ETHERNET-MIB and so on): a tab for each table and a form for each group of single values. What the main menu already shows (interfaces, addresses, routes, ARP, storage, the system name) does not repeat there. Names, types and value lists come from a built-in dictionary of 30 standard modules and the net-snmp modules; values are shown as a person reads them: states by name, times as durations, MAC and IP addresses as such, yes and no. A window of the "MIB" group reads at most 1000 rows of a table and refreshes every 10 seconds.

A subtree the dictionary does not know, a maker's own objects under enterprises for example, shows as a window named after the maker (MikroTik, Cisco, Huawei, ...) with one row per object: OID under the subtree, type and value, at most 2000 rows.

Writing needs a community or a user with write rights. Any column the dictionary marks read-write or read-create can be changed; all the changes of one row go in one request, which the agent applies whole or not at all. Rows are added and removed in tables with a RowStatus column (VLANs of Q-BRIDGE-MIB, SNMP targets, communities, VACM views): the new row needs its index first (for a table numbered by one integer the window proposes the next free number), and the program sends createAndGo, or createAndWait, the values and active to an agent that wants the row built in steps; a row the agent does not accept is removed again. Tables without RowStatus remove rows only where the standard gives a value for it, such as `invalid` of dot1dStaticStatus. A value of an unknown OID can be changed in the type the agent reported; counters are never written. SNMP tables have no order, so rows cannot be moved. There is no rollback like Safe Mode: a wrong change of a VACM, USM or community table can lock the program out of the agent.

## Safety

If a router changes its certificate or its SSH key, the program tells you: it remembers the fingerprints of the certificates and keys you accepted. Protocols without encryption are marked in the connection window and in the main window. "Settings" has "Hide passwords and keys" (they stand as dots in tables, dialogs and the journal, and the eye in a field shows the value) and "Ask before removing from the router".

### Safe Mode

Safe Mode protects against an edit after which the router stops answering. How it works depends on the router.

On RouterOS press Safe Mode in the top bar. While it is on, the router takes the settings back by itself if the connection is lost. The button turns into a menu with a count of edits: "Keep changes" keeps them, "Roll back changes" undoes them. If you close the connection without choosing, the program asks whether to keep the edits.

On VyOS the button turns on commit-confirm for every edit. If the program is left without a connection after an edit, VyOS reboots in about a minute with the configuration saved before it.

On OpenWrt, OPNsense and pfSense the top bar has an Apply button instead of Safe Mode: it puts the edits you made into effect. On OpenWrt the apply goes through `uci apply` with a rollback, and if the connection is lost after it, the router returns to its previous configuration. On OPNsense 24.7 the rules of the firewall are rolled back, and the API of 26.7 has no rollback. pfSense has none at all. Where there is no way back, the program says so.

## In a browser

A browser cannot open connections to routers on its own, so a gateway stands between the two. It keeps the saved routers and their passwords and connects to the routers in place of the page.

**From the desktop app.** "Settings", "Access from a browser…". Set a password (you log in as `admin`), choose a port and press "Open the access". The window shows the addresses of the computer and the fingerprint of the certificate; there is a QR code for a phone. Open the address in the browser of a phone or of another computer on the same network. The browser warns once about the self-signed certificate: compare its SHA-256 fingerprint with the one in the window and go on. While the access is open, its port shows in the title of the window, and the next start of the app opens it again. The box "Any address, not only the local networks" is for access from outside the home network (through a forwarded port or a VPN); the gateway then asks for a code from an authenticator app every time (Google Authenticator, Aegis, 2FAS and the like).

**As a separate gateway.** The archive of the gateway (`NetworkHelm-gateway-<version>-windows-x64.zip` or `-linux-x64.tar.gz`) unpacks and runs without any Java installed: `networkhelm-gateway.bat` on Windows, `./networkhelm-gateway.sh` on Linux. The password of the first start shows once, in the console window or in the log; if you lose it, set a new one with the `--reset-password` option. The gateway also runs as a jar (Java 17 or newer is needed): `java -jar NetworkHelm-gateway-<version>.jar`; the address of the Docker image, if one was published, is in the description of the release. Then open `https://<address of the computer>:8443`. By default the gateway answers local networks only; the `--public` option opens it to any address and makes the code compulsory, and `--code` asks for the code on the local network as well.

**Straight on an OpenWrt router.** A router with LuCI can serve the page itself and reach only itself through `/ubus`; a page served that way has no terminal and no files.

More about the gateway (all options, Docker, a container on a RouterOS router, a systemd service) is in [server/README.md](server/README.md).

**The demo page.** https://vasmarfas.github.io/networkhelm/ shows the interface on made-up routers. It has no gateway, and a page in a browser can only send HTTP, so it cannot reach most real routers. RouterOS does not help: its REST API sends no CORS headers and answers the preflight request with 503 (the REST API page of MikroTik says so), so a page cannot call it even over HTTPS with a trusted certificate. Chrome's Direct Sockets, which would give a page real TCP, are exposed only to isolated contexts such as installed Isolated Web Apps, not to ordinary pages. How that page is built and what it can do is in [app/webApp/README.md](app/webApp/README.md).

## Network tools

The "Network tools" button in the connection window and the wrench in the top bar of a router open fourteen tools that run on this computer or phone, not on the router.

| Tool | What it does | Where it works |
|---|---|---|
| Ping | Echoes through the system `ping` (on Android `/system/bin/ping`, no root needed; on iOS an ICMP socket that needs no privileges) or, as a second method, the time to open a TCP connection to a port (443 by default). A count or "until stopped", the interval, the timeout, the packet size, the TTL, the don't-fragment flag, and IPv4 or IPv6 to force; the address the name resolved to is shown. A chart of the last 100 round-trip times (a lost reply is a red bar), the last 20 replies, and sent, received, lost in per cent, minimum, average, maximum and jitter (the deviation of the times from their average). "Find path MTU" sends echoes of different sizes with the flag set and narrows in on the largest one that passes (IPv4 only, from 576 to 1500 bytes) | Desktop, Android, iOS |
| Traceroute | The same `ping` with TTL from 1 to 30; each hop with its address, host name and time. The name is a reverse lookup through the system resolver that runs after the hop is shown, waits at most 2.5 s and can be turned off. It stops at the target or after eight silent hops in a row | Desktop, Android, iOS |
| Port scanner | TCP connections to a list or a range of ports of one host (`22,80,443`, `1-1024`), 64 at once by default, 800 ms each; a port that does not connect is shown as closed or filtered | Desktop, Android, iOS |
| LAN scanner | Scans a range: `192.168.1.0/24`, `192.168.1.10-100`, `192.168.1.10-192.168.1.99` or an address with a mask, at most 4096 addresses (the network and the broadcast address of a subnet are left out). It starts with the /24 of this device and, if there are several networks, offers a list. Every address gets an echo (48 addresses at once) and TCP connections to ports 22, 53, 80, 139, 443, 445, 5000, 8080, 8291 and 62078; a host that answers either is listed with its name, MAC address, vendor, round-trip time and open ports. MAC addresses are read from the ARP table of this device, and a host that is in the table but ignored every probe is listed too; iOS and Android 10 and newer close the table to apps, and there the list has no MAC address and vendor columns | Desktop, Android, iOS |
| DNS lookup | A, AAAA, MX, NS, TXT, CNAME, PTR, SOA, SRV and CAA over UDP from Cloudflare, Google, Quad9, Yandex or any server you type; a truncated answer is asked again over TCP. An IP address is looked up as PTR | Desktop, Android, iOS |
| Whois | Two tabs. RDAP asks the registry over HTTPS about a domain, an IP address, a network in CIDR form or an AS number and lists status, dates, name servers, registrar and the contacts the registry makes public as rows; the raw JSON is one tick away. The server comes from the IANA files at data.iana.org, rdap.org stands in when they name none. Port 43 asks whois.iana.org, follows its referral to the registry and, when the registry names one, to the registrar; a server that fails leaves on the screen what it had sent and is named under the text | RDAP: Desktop, Android; port 43: Desktop, Android, iOS |
| IP info | An address, a host name or nothing (your public address). Shows the addresses a name resolves to, the reverse name, the AS, prefix, country and registry from the DNS service of Team Cymru, the network record from RDAP with the abuse contact, and the location and provider from ipwho.is (ipapi.co if that fails); for your own address also the address of the other family from ipify. Every block names the host it asked and fails on its own | Desktop, Android |
| Speed test | Latency (median and jitter of five requests), download and upload over four parallel connections to speed.cloudflare.com or to another server with the same /meta, /__down and /__up; the first half second of a phase is not counted, the next 8 s are, and the figure on the screen is live. Stop cuts the connections | Desktop, Android |
| Wake-on-LAN | Sends the magic packet to a MAC address by UDP broadcast (255.255.255.255, port 9 by default) | Desktop, Android, iOS with the multicast entitlement |
| Subnet calculator | Network, mask, wildcard, broadcast, first and last host, number of hosts, class and the binary form for IPv4; network, first and last address and their number for IPv6. A range (`192.168.1.10-192.168.5.110`, or `192.168.1.10-100` where the number is the last octet) gives its first and last address, their number, the fewest CIDR blocks that cover it exactly and the smallest network around it | Everywhere |
| Subnet splitter | Three modes. Equal cuts a network, or a range that is exactly one network, into parts by their number (rounded up to a power of two) or by a prefix; the table shows up to 1024 parts. VLSM gives every host count its own block, the biggest first, inside a network or a range; a block is never smaller than a /30. Summarize merges a list of networks and ranges, one per line or separated by commas, into the fewest CIDR blocks | Everywhere |
| Transfer time | Gives the third of size, speed and time when two are typed: sizes from B to TiB (decimal and binary), speeds from bit/s to GB/s, time in hours, minutes and seconds. Overhead in per cent is the share of the speed that carries no data. For a known size the time at 10 Mbit/s, 100 Mbit/s and 1 Gbit/s is listed under the result | Everywhere |
| Port reference | 109 well-known TCP and UDP ports with the protocol, the service and a short description in the language of the interface. The filter takes the start of a number, a part of the service, the protocol or a word of the description. The port scanner names open ports from the same list | Everywhere |
| MAC vendor lookup | Finds the vendor in the IEEE registry that comes with the program (58 623 blocks of 2026-09-25); the longest prefix wins | Everywhere |
| IP ↔ HEX | Turns IPv4 addresses into the hex value of a DHCP option as RouterOS takes it (`10.103.0.250` → `0x0A6700FA`); with a sub-option code it adds the code and the length, as option 43 wants them (`1` gives `0x01040A6700FA`). A browser can open no sockets, so the page shows the calculator, the splitter, the port reference, the transfer time, the MAC lookup and IP ↔ HEX. On iOS the echoes of the ping, the traceroute and the LAN scanner go through an ICMP socket that needs no privileges.

RDAP, IP info and the speed test send requests to third-party hosts, which the line under their form lists. They need HTTPS with the certificate check of the system, which the desktop and Android have; on iOS only the port 43 whois remains of the three, in a browser none.

The scan sends many packets, so run it only on networks you manage. On Android 10 and later the ARP table is closed to apps, so the scan shows no MAC addresses there and misses the hosts that answer nothing but ARP. A MAC address with the "locally administered" bit set, which phones use for privacy, has no vendor and is marked "random or local".

## Appearance

Settings → Theme offers three themes. Modern is the default: flat controls in the layout of WinBox 4. Legacy repeats WinBox 3, with raised buttons and framed tabs, and stays light until "Look" is set to Dark. Material follows Material Design 3: pill-shaped buttons, rounded windows with a thin frame, tonal selection of the current item, and the title of the active window in a tint of the accent. Its sizes are made for a mouse: table rows 26 dp high against 24 in Modern, fields and window titles 32 dp; on a phone every theme grows to 40 dp for a finger. "Table rows" in the same settings adds up to 8 dp to every row of a table or takes 2 away. "Comments in tables" puts the comment of a row above it, in a column or nowhere, in every table. The comments button of a table window gives that table a mode of its own and stays highlighted while it has one; "As in the settings" at the top of its menu returns the table to the setting, and a change of the setting returns every table to it. "Colour" picks one of eight accents, and Material builds both its light and its dark palette from it. On Android 12 and later "System colours" takes the palette Android builds from the wallpaper instead. "Look" chooses between light, dark and the setting of the system; Modern and Material follow the system until it is changed.

A settings window opens its tables with buttons, as in WinBox: Static, Cache, Adlist and Forwarders of IP › DNS open one window "DNS" with a tab for each, and a second button switches that window to its tab. "Open the tables of a settings window as its tabs" in Settings puts them on tabs of the settings window instead, and the window grows to show the whole form; the same holds for SNMP, NTP, UPnP, NAT-PMP, RoMON and Accounting of RouterOS 6. Windows that were open before the change keep their layout.

A group of the left menu opens as a panel beside the menu. "Open the groups of the left menu downward" in Settings lists its windows under its name instead, as the web interface of Keenetic does, and makes the menu 40 dp wider for their names; a narrow window always lists them so.

The app's own messages are in the language of the interface: with the Russian interface an error of a connection, a field check or a window is in Russian. A text the router sent is shown as it came.

The transfers of the Files window and the session of a terminal belong to the connection, not to the window. A minimized window or one under others does not stop them; a closed Files window leaves its transfers running, and opened again it shows their queue. Disconnecting from the router stops them.

## When something does not work

| What you see | What it means | What to do |
| --- | --- | --- |
| "… does not accept connections on port N: the service is off or the port is closed" | the service on the router is off, or the firewall closes the port | turn the service on (on RouterOS, for example, `/ip service enable api`) or pick another protocol; grey entries in the list are the ports that gave no answer |
| "… does not answer" | a wrong address, no route, or a firewall that silently drops packets | check the address, ping the router, make sure you are on the same network; if the router sits behind another router, use the "Via router" field |
| "… cannot be found" | the name does not resolve to an address | enter the IP address |
| "The router refused the login: …" | a wrong login or password, or the user has no rights for that service | check them and, on RouterOS, the user group |
| "… and NetworkHelm could not agree on TLS …" | API-SSL is on in RouterOS, but the service has no certificate | pick "API (8728)", connect, and issue a certificate in the "Prepare router" window |
| "No SNMP answer from …" | the community is wrong or is not allowed to read (a switch counts such a request as "illegal operation for community name supplied"), the agent is off, or UDP 161 is closed | on the agent check the community: it must exist with read rights and let your address in; SNMP v2c must be on |
| "the SNMP agent answered notWritable for …" (or noAccess, readOnly, authorizationError) | the object is read-only on this agent or the community or user may not write it | use a community or user with write rights and a view that includes the object |
| "the SNMP agent answered inconsistentValue for …" (or wrongValue, wrongLength, noCreation) | the agent does not take this value or this row: a required column of a new row is missing, the index is taken, the value is out of range | fill the other columns of the row, take another index, check the allowed values in the documentation of the device |
| "Android does not let NetworkHelm reach the local network" | the permission is not granted | in the Android settings of the app allow "Nearby devices" |
| "The connection was lost after sending the command …" | the link dropped at the moment of the edit | check the router first: the command may have run, and a repeat would run it twice |
| "The connection to the router is lost, reconnecting…" | the link dropped or the router rebooted; on a phone the system also closes the connections of an app in the background | wait: the session comes back by itself, open forms keep what you typed; after a return to the app on a phone this takes a few seconds |
| "Loading… 2187 of 34998" at the bottom of a list | over TCP 8291, SSH and REST a table of more than 2 000 rows comes in portions, so that the router does not have to hold it in memory whole; on a local network 30 000 rows take about 10 seconds over REST and 40 over TCP 8291 | wait: the list is ready when the count turns into the number of items |
| "Not loaded" and a "Retry" button under a list | the rows did not arrive; the reason stands beside the button | press "Retry" or F5 |
| The router stopped answering right after you typed the address | its protection against password guessing took the port check for a login attempt | wait for the block to end and turn the check off in "Settings" |
| "The browser blocked the request …" | a page in a browser can only send HTTP, and RouterOS sends no CORS headers | open the app through a gateway, or connect with the app |
| The program does not start | on a computer it writes the cause to the file `NetworkHelm-startup-error.log` in the temporary folder | take the file (`%TEMP%` on Windows, `/tmp` on Linux) and attach it to your report with the version of the system |
| A window closes after a message about an error | the error is written to `NetworkHelm-error.log` in the same temporary folder, and the message gives its full path | attach that file to your report |

Everything else can go to the [issue tracker](https://github.com/vasmarfas/networkhelm/issues). Leave addresses, passwords and keys out of your reports.

## Where the data lives

The program keeps saved routers, settings and table layouts in its own data folder. Passwords and keys you asked it to remember are in the protected storage of the system: Windows Data Protection on Windows, the Keychain on macOS and iOS, the Secret Service on Linux, the Android Keystore on Android. Where there is no system storage, the program encrypts them itself, and that protection is weaker. All of it is described in [privacy-policy.md](privacy-policy.md).

On a computer several copies of the program can run at once, as WinBox does, a window for each router. Before each write a copy reads the file again and puts its change onto what the file holds now: a router saved in one copy does not vanish when another saves, and the same holds for settings, themes, snippets, table layouts, tunnels and passwords. Routers and passwords another copy saved show when the connection window opens; settings another copy changed show in this one after a restart.

### Synchronisation

Synchronisation keeps the saved routers and the rest of your work alike on your computers, phones and the page on GitHub Pages. It is off until you set it up, and until then the program sends nothing for it anywhere. Once set up, it sends only encrypted files, and only to the services you choose: no server of the developer stands between your devices.

What goes: the saved routers, the trusted fingerprints of certificates and host keys, the settings that do not depend on the device (language, theme, dark mode, accent colour and system colours, comments in tables, the question before removing from the router, hidden passwords, the check for new versions), themes, terminal snippets, Docker templates, whose .env keeps the names of the variables and none of their values, and the named workspaces and tunnels of each router; under "What goes" each kind has a box of its own. The passwords and keys of the routers (passwords, SSH keys and their passphrases, SNMP privacy keys) go only with the box "Passwords and keys of the routers", which is off at first; on the other device they go straight into its protected storage. Each device keeps to itself the scale, the recognition of the device while an address is typed, the look of tables and of the menu, the resource bar, the split of the connection window and the lines the terminal keeps, as well as the layouts of tables, the workspace without a name, the view of the menu of a router, the window of the program and the cached menu descriptions.

Settings → "Synchronisation…" → "Set up…" starts with the service:

- a folder on a computer, on Android or in Files on iOS that Syncthing or the client of Dropbox, OneDrive, Yandex Disk, Mail.ru Cloud, Nextcloud or iCloud Drive keeps alike; each device picks its folder itself, and the program works only in its subfolder `networkhelm-sync`;
- Dropbox, in the folder of the app Apps/NetworkHelm, the only one the program sees there: you sign in in the browser, and on a phone the browser comes back to the program by itself; the page signs in only at https://networkhelm.vasmarfas.com/;
- Google Drive, in the hidden folder of the app, which takes space on the drive but is not shown among its files: on a computer, Android and iOS, not on the page, since Google gives a page no sign-in without a server of its own;
- Yandex Disk, in the folder of the app Applications/NetworkHelm: everywhere, the page at that address included;
- iCloud, in the CloudKit container of the app, signed in with an Apple ID: everywhere; a computer and Android sign in through the page at that address, which hands the answer back to the program;
- WebDAV: Nextcloud, ownCloud, Synology, Yandex Disk (`https://webdav.yandex.ru`) or Mail.ru Cloud (`https://webdav.cloud.mail.ru`), with an app password made for NetworkHelm;
- S3: MinIO, Yandex Object Storage, Selectel or AWS, with a key for this bucket alone;
- Git: a private repository on GitHub (a fine-grained token with Contents: Read and write), GitLab (a project token with the scope `api` and the role Developer, Maintainer if the branch is protected) or Gitea (`write:repository`), with a token for that repository alone;
- your NetworkHelm gateway, the server or the desktop program with access from a browser on: its address, user, password and the code of the authenticator app, for which the device gets a token.

The address of a service must start with https://. A server whose certificate the system does not trust asks about its fingerprint the way a router does, above any window, but only when it is a server of your own: an IP address, a local name such as nas.local, or a port other than 443, as the gateway takes. A public service with a certificate the system does not trust is refused, since someone stands between you and it. Where the system has no protected storage for the keys, the window says that the program encrypts them itself.

An empty service gets a new vault. Its password must be at least 12 characters long, must not be on the list of the most common passwords and must take more than 10^10 guesses by an estimate in the manner of zxcvbn; the line under the field says what makes a password weak. With 256 MiB of memory a guess, 10^10 guesses are about a year of work for one graphics card. "Make up a phrase" gives five words of the EFF list, about 64 bits, beyond any such search. "Extra protection" adds a secret key of 128 bits, shown once as 26 letters and digits in groups of four: without it a copy of the vault cannot be guessed at all, and a new device needs it as well as the password, unless it takes the code of a device already in the vault. Forget the password and lose every device, and the data cannot be opened: the service has no key. The key is made from the password with Argon2id, 256 MiB of memory and 3 passes, which takes a few seconds on a computer and longer on an old phone; a password counts the same however a system composes its letters. Every file is encrypted with XChaCha20-Poly1305 and checked when it is read: a file changed on the service, put in the place of another or given back from before is not taken. The service sees that you keep a NetworkHelm vault, how many devices write to it, when they write, and its size to 4 KiB.

A service that holds a vault already lets a second device join it with the password. The other way is a code: on a device already in the vault "Show the code…" asks for the password again and shows a QR code, with the same code as text under it, for 60 seconds; the text cannot be selected, so it stays out of the clipboard. The code opens all your data, so show it to nobody else. On the new device "I have a code from another device" takes the text, and a phone scans the QR code with its camera, asking for the camera only then. Before the device joins, the window names the service and the devices of the vault: join only if they are yours. The code of a folder holds no folder, and the new device picks its own; the code of WebDAV, S3, Git or the gateway carries the login of the device that showed it, so the service sees one login for both, and revoking it stops both. A device with too little memory for Argon2id joins this way too.

A round goes at the start, two seconds after an edit, at once when the window comes back to the front, once a minute while it stays in front and every 15 minutes behind it. The gateway tells of a change at once; with the other services an edit from another device shows within a minute while the program is in front. Edits made without a network wait and go with the next round. Each router, password, snippet and setting merges on its own, field by field: when one device changed the port of a router and another its comment, both changes stay, and of two edits of one field the later wins. A removal is kept for 180 days, and a device that comes back after a longer absence does not bring back what was removed meanwhile. Of two copies of the program on one data folder only one synchronises, and the edits of the other go through it.

The window of synchronisation shows the service, how the last round went and "Synchronise now". Under "Devices" stand this device, which you can rename, and the others with their system, the version of the program and when each was last there; a device updates its line with each state it writes, after a change of its name, system or version, and once a day, and a device whose files left the service leaves the list. "Turn off…" beside another device asks for the current password and a new one and makes a new key of the data: the device turned off reads nothing written after that, its files leave the service, and the other devices ask once for the new password. What it read before stays on it, and its login to the service is revoked in the settings of the service itself. "Change the password…" asks for the current password too. The key of the data stays, so the other devices go on without the new password; "Change the key of the data as well" is for a password someone else may know, since an earlier copy of the vault, in the history of the service or of a sync client, still opens with the earlier password. "I forgot the password" sets a new password without the current one, which whoever uses this device can do; the key of the data changes with it, so every other device stops and asks for the new password, and the change cannot pass unnoticed. With extra protection each new key of the data comes with a new secret key, shown once, and a device that asks for the new password needs it as well. "Move to another service…" moves the whole vault with the same keys; move the other devices as well, or give them the code. "Add a place…" keeps one more whole copy of the vault in another service, picked as in the wizard, and this device keeps every copy up to date: devices that use different places get the data of each other through it, and a new password or key made on a device of one place reaches the vault of the others with its next round. A place that does not answer shows under the state as "Not synchronised with" and the reason, while the others go on. "Remove" beside a place takes the files of this device from it; the vault and the files of the other devices stay there for the devices that keep using it. A cloud can be one place only. "Turn off…" at the top removes the keys and the login of the service from this device and leaves the data on it. With "Also remove the vault from the service" every device stops and the vault cannot be brought back; each device keeps its own data.

When two devices trust different keys for one address and port, synchronisation does not choose: each device keeps its own, and "Disputed fingerprints" shows both. Two routers behind one address, such as 192.168.88.1 at home and at work, give such a dispute too, since a fingerprint is kept per address and port; left unanswered, it leaves each device with its own key. "Take the other" puts the key of the other device here; "Keep this one" sends this key to the others, and the question goes to them. A file the service gave back from before, or one written under an earlier key, shows under the state as "Not taken" with the reason. A vault the service gives back from before the key changed, from a copy or from its history, stops every device: the one that holds the newer key says so, and the others write nothing until the new password opens the vault. "Change the password…" → "I forgot the password" on the device that changed the key last puts a vault with a newer key in its place.

Beside the settings, in the toolbar of a router and in the header of the connection window, a cloud with a check mark means synchronised, two circular arrows a round under way, and a red cloud with an exclamation mark a failure; the mark opens the window. While synchronisation is off there is no mark.

The page on GitHub Pages synchronises like the program, without a folder. A page reaches only a service that lets pages of other addresses read its answers (CORS). The NetworkHelm gateway lets in the page on GitHub Pages, but the page cannot pin the certificate of the gateway: open the address of the gateway in a tab of the browser first and accept the certificate there. A WebDAV server or an S3 bucket lets the page in once its owner allows its address; the window warns of both when you pick them. The keys and the remembered router passwords stay in the local storage of the browser under a WebCrypto key that the page cannot export, and survive a reload. A copy of the browser profile does not open them, but a script on the same address does, and the address of the page is shared by every GitHub Pages site of the same account; while the page is open, the keys are in its memory. A phone takes a photo of the code with its camera and the browser finds the code in it (Chromium on Android, ChromeOS and macOS); elsewhere type the text. The page that a gateway or a router serves has no synchronisation: it works with the data of that host. The desktop program synchronises the data its gateway shows, while the gateway server keeps its routers to itself and takes part only as a service for the other devices.

Synchronisation is new in 1.4.0. Named workspaces and tunnels saved before it go to the other devices once the tab of their router has been opened in 1.4.0, and a tab that is open while they change on another device shows the change after it is opened again. A version that does not know a kind of data from a newer one passes it on untouched; a vault that needs a newer version stops with a request to update the program. The gateway gives each device that logs in a token of its own but takes them back only all at once, with a new password of the gateway. Git keeps every write as a commit, so the repository grows by the size of the state each time. Checked: two copies of the program with separate data folders through a WebDAV server, the services against Apache mod_dav, MinIO and Gitea, and an Android phone that joined with a code and exchanged routers both ways; iOS, the camera of a phone and the page in a browser were not checked on real devices for this release.
